The repository contains substantial, test-covered email-platform functionality,
but the production API boundary is not yet internally consistent or aligned
with the approved Keycloak and Codestra Middleware contracts.

The highest-impact defects are not cosmetic. They affect password authority,
cross-system delivery guarantees, lifecycle-state accuracy, browser-session
security on the candidate BFF branch, and CI/release governance.

## Review method

This review intentionally did not attempt a broad “fix all” change.

It first located:

1. the API application and mounted routers;
2. the SMTP relay and delivery workers;
3. the existing test entry points;
4. the current default-branch and open-branch state;
5. the Keycloak and Middleware integration boundaries;
6. concrete defects that can be repaired in dependency-ordered slices.

No container, server, DNS, Nginx, Keycloak realm, Postal service, SMTP
credential, database, or live-delivery control was changed by this audit.

# Findings

## API-P0-001 — production still has a second password authority

**Location**

```text
apps/gateway/app/main.py
POST /v1/auth/forgot-password
POST /v1/auth/reset-password
```

`POST /v1/auth/login` fails closed to canonical OIDC in production, but the
forgot/reset endpoints do not apply the same Keycloak-authority gate.

The forgot endpoint creates a local reset hash and expiry. The reset endpoint
consumes the local token, writes a local password hash, and revokes local
sessions.

This violates the approved rule:

```text
PRODUCTION_HUMAN_PASSWORD_AUTHORITY=KEYCLOAK_ONLY
```

There is also a functional defect: the forgot endpoint never delivers the raw
local reset capability. It stores only the hash and returns a generic response,
so the local flow is both unsafe as an authority boundary and unusable as a
complete recovery workflow.

**Required repair**

When Keycloak is enabled or the environment is production:

```text
POST /v1/auth/forgot-password -> generic KEYCLOAK authority response/redirect
POST /v1/auth/reset-password  -> 409 PASSWORD_AUTHORITY_KEYCLOAK
local password mutation       -> prohibited
local reset token generation  -> prohibited
```

Add regressions proving no local reset hash, password hash, session mutation, or
email task occurs under Keycloak authority.

## API-P0-002 — Klyrow and Middleware do not implement one exact contract

**Location**

```text
apps/gateway/app/main.py::emit_middleware
Keycloak/config/contracts/service-access-matrix.json
Keycloak/config/contracts/webhook-contracts.json
```

The reviewed identity contract requires:

```text
caller=klyrow-gateway
grant_type=client_credentials
audience=middleware-api
scope=email.events.publish or email.inbound.publish
path=/api/v1/klyrow/events
X-Codestra-* signature/idempotency headers
```

The Klyrow implementation currently uses a configured bearer API key,
`X-Klyrow-*` signature headers, `klyrow.email.*` event names, and either a custom
`KLYROW_EMAIL_EVENT_URL` or legacy `/api/v1/klyrow/{events|bounces|complaints|unsubscribes}`
paths.

Both sides may be individually hardened, but they are not the same protocol.
That is an integration failure, not documentation drift.

**Required repair**

Create one versioned contract package and make both repositories validate:

```text
method
path
OIDC issuer/audience/authorized-party/scope
HMAC canonicalization
required headers
event type vocabulary
JSON Schema
idempotency semantics
replay window
tenant resolution
error envelope
retry classification
```

Do not support two “canonical” event paths indefinitely.

## API-P0-003 — the initial queued event is not durably delivered

**Location**

```text
apps/gateway/app/main.py::_send
apps/gateway/app/main.py::emit_middleware
```

The API commits the message, event, idempotency record, usage row, and optional
Postal outbox row. It then calls `emit_middleware()` after commit and ignores the
returned `False` value.

If Middleware is unavailable, the customer receives a successful 202 response
and the local message remains committed, but the `klyrow.email.queued` lifecycle
event has no durable cross-system retry record.

Postal callback events do have a retry/DLQ record, which makes the missing
queued-event outbox especially inconsistent.

**Required repair**

Insert a transactional integration-outbox row in the same database transaction
as the message. A worker must deliver it with leases, bounded retries, replay
protection, and a dead-letter state. No synchronous network call should be part
of the API success transaction.

## API-P0-004 — provider acceptance is recorded as delivery

**Location**

```text
apps/gateway/app/main.py::email_outbox_loop
```

After Postal accepts `/api/v1/send/message`, the generic outbox row is marked:

```text
state=delivered
```

Postal API acceptance proves provider submission, not recipient delivery.
Recipient delivery must be established by a verified provider lifecycle event.

This can corrupt customer status, billing, reconciliation, support decisions,
and delivery-rate metrics.

**Required state model**

```text
PENDING
PROCESSING
PROVIDER_SUBMITTED
SENT
DELIVERED
DEFERRED
BOUNCED_SOFT
BOUNCED_HARD
COMPLAINED
FAILED
DEAD_LETTER
```

The provider response ID should be persisted at `PROVIDER_SUBMITTED`. Only a
signed Postal lifecycle event may advance to `SENT` or `DELIVERED`.

## API-P1-001 — CI grants write capability to pull-request jobs

**Location**

```text

```

The workflow runs on `pull_request` but grants workflow-level permissions:

```text

security-events: write
attestations: write

```

Those capabilities are not needed by the ordinary test job and should not be

```text

actions/setup-python@v6
docker/setup-buildx-action@v3
docker/build-push-action@v6
```

Only some actions are exact-SHA pinned.

**Required repair**

```text
workflow permissions = contents:read only
job-level elevation = publish job only
pull-request OIDC = prohibited
pull-request package writes = prohibited
all external actions = exact reviewed SHA
persist-credentials = false
source-head and merge-result jobs = separate
```

## API-P1-004 — SMTP credential creation permits unusable multi-stream credentials

**Location**

```text
apps/gateway/app/provider.py
POST /smtp/credentials
apps/gateway/app/smtp_policy.py
apps/gateway/app/smtp_relay.py
```

The credential API accepts any nonempty subset of known streams. The relay
requires exactly one stream through `select_credential_stream()`.

An API-created credential can therefore be valid according to the management
API but unusable according to the SMTP server.

**Required repair**

```text
len(allowed_streams) == 1
```

For Keycloak:

```text
allowed_streams=["SECURITY"]
allowed_senders=["security@codestra.co"]
```

Add API and SMTP authentication tests for zero, one, duplicate, and multiple
streams.

## API-P1-005 — rate limiting is process-local

The primary API rate limiter uses an in-memory `defaultdict(deque)` keyed by
tenant. This does not provide a production limit across multiple workers or
containers and resets on restart.

Unauthenticated authentication/reset limiting is also process-scoped unless the
candidate BFF work replaces it.

Move authoritative limits to Redis or another atomic shared store and define
fail-closed behavior for high-risk endpoints when the limiter is unavailable.

## API-P1-006 — bulk email has partial-commit semantics

`POST /v1/email/bulk` iterates through individual send operations. Each item can
commit independently. If a later message fails, earlier messages remain
committed while the batch request fails.

Define one of these explicit contracts:

```text
atomic batch
or
per-item result envelope with durable batch identity and replay semantics
```

Do not expose accidental partial success as a generic request failure.

## API-P1-007 — API documentation and implementation lack a drift gate

`docs/API.md` documents `/v1`, bearer authentication, idempotency, request IDs,
and `/v1/developer/openapi.json`, but the repository does not commit a generated
OpenAPI snapshot or endpoint-policy registry and CI does not compare runtime
routes against one.

The code also contains aliases and hidden routes, multiple webhook paths, and
multiple authentication methods. These need explicit lifecycle status rather
than implicit discovery from decorators.

Required generated artifacts:

```text
openapi.json
endpoint-registry.json
webhook-contracts.json
route-owner matrix
API diff summary
```

CI should fail on an unowned route, duplicate operation ID, undocumented
mutation, missing auth policy, or method/path removal.

## API-P1-008 — domain verification input and DNS execution are under-specified

The basic domain model uses a permissive regular expression and the verification
handler catches every DNS exception as a simple false result.

The API should normalize IDNA, reject invalid labels/consecutive dots/trailing
hyphens/oversized names, use bounded DNS timeouts, distinguish NXDOMAIN from
transient resolver failure, and keep verification evidence and timestamps.

## API-P2-001 — the core application is too monolithic

`apps/gateway/app/main.py` is approximately 70 KB and mixes:

```text
models
authentication
rate limiting
canary policy
Middleware transport
Postal webhook processing
provider retry workers
generic email delivery
health/metrics
business APIs
HTML portal serving
router composition
```

This increases review risk and makes policy drift easier.

Decompose only after route and behavior contracts are locked. Use compatibility
routers and regression tests so modularization does not silently change
methods, paths, dependencies, or status codes.

## API-P2-002 — response and status semantics are inconsistent

Examples include:

```text
/v1/messages and /v1/email/* aliases
accepted_test vs queued vs accepted vs delivered
provider_message_id initially equal to the local message ID
hidden compatibility routes without retirement metadata
```

Adopt a versioned error envelope, canonical lifecycle enum, provider/local ID
separation, and explicit deprecation metadata.
